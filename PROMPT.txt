当运营人员改动一条正在生效的限流规则时，眼下的做法是改完立刻对全部命中流量生效：新阈值一推送，所有网关实例同时切到新规则，没有任何缓冲。真实运维里这很危险——把某个接口的客户端配额从 100 收紧到 20，一旦判断失误，全部真实客户瞬间被大面积拒绝，等发现问题再改回去，损失已经造成。这一版要为规则变更引入按比例分批放量的能力：一次改动可以先只对一小部分流量套用新规则，其余流量继续走原规则，观察一段时间没问题再逐步扩大比例，直到全量；中途发现新规则表现不好，能立刻把这次放量收回、让全部流量瞬间退回改动前的老规则，不留残留。

请在现有的规则配置、判定与观测体系上增加这一层「灰度放量」。运营人员保存一次改动时，除了新的规则内容，还能声明这次改动的放量比例（例如先 10%），此后这条规则同时存在两个版本：一部分命中流量按新版本判定、其余按旧版本判定，两个版本各自独立占用自己的配额计数，互不挪用。放量比例可以随时调整（10% → 50% → 100%），到 100% 即视为新版本全量生效、旧版本可以退场；也可以把比例调回 0 或直接中止这次放量，效果等同于本次改动从未发生、全部流量立即回到旧版本。这套机制必须在多实例横向扩容下保持一致：同一笔请求无论落到哪个网关实例，都要被分到同一个版本上，不能因为实例不同而一会儿走新、一会儿走旧。

分桶必须是确定性的、可复现的，而不是每来一笔请求各自掷一次骰子。同一个判定主体（比如同一个客户端标识、或规则声明的那一组维度值的组合）在放量比例不变的期间，必须稳定地落在同一侧：要么一直走新版本、要么一直走旧版本，不能同一个客户端这一秒被判到新版本、下一秒又被判到旧版本，导致它一会儿宽一会儿严。当比例从 10% 提高到 50% 时，原本已经在新版本里的那 10% 主体必须继续留在新版本，只是再把一部分老版本里的主体迁进来，而不是把所有主体重新洗牌一遍——放量应当是单调地把流量往新版本搬，扩大比例只增不减地纳入主体。这个「谁在新桶、谁在老桶」的划分要能被明确算出并复现：给定规则、放量比例和一个判定主体，结果唯一确定，任何一个网关实例、任何时刻算出来的归属都一样。

判定入口要如实反映这套机制：一笔请求进来，先按它所属的版本选出对应的规则内容，再走原有的多维匹配与多级配额级联判定。新旧两个版本各自的配额是完全隔离的两套计数，新版本里的客户端打满了不影响老版本同一个客户端的余量，反之亦然；放量中止、流量退回老版本后，新版本那套计数不应再干扰任何判定。响应里除了原有的放行/拒绝与命中级别，还应能看出这笔请求当时是被判给了新版本还是旧版本，方便排查「为什么同一个接口两个客户体验不一样」。

配置校验要守住这套机制的边界：放量比例只接受 0 到 100 之间的合法取值，越界或非数值的比例要被拒绝并说明原因；一条规则在没有处于放量过程中的时候，就是单一版本的普通规则，不能凭空冒出一个不存在的「新版本」参与判定。既有的规则合法性校验（阈值非正、维度值缺失、算法未知、窗口长度非法等一律拒绝并给出原因）在灰度场景下同样要对新版本内容生效——不能因为只灰度一部分流量，就放任一个非法的新版本混进来判定。

前端的观测台要能把灰度过程看清楚。运营人员在编辑规则、准备提交一次改动时，能设定本次的放量比例；对一条正在放量的规则，观测区要能分别呈现新版本与旧版本各自的放行/拒绝走势与配额占用，让人直观对比「新规则收紧后拒绝是不是涨了、涨了多少」，从而决定是继续扩大比例、维持、还是收回。页面上原有的发压/回放能力要能配合这套机制使用：对一条正在灰度的规则回放一段流量，应当能看到这批流量按比例被分流到两个版本，两条曲线各自累计，并且反复回放同一批主体时，分流结果稳定不变。放量比例的调整（含调到 100% 全量、调回 0 或中止）都要在页面上即时可操作、即时生效，无需重启任何网关进程，也无需手工去后台改数据。

放量状态本身要能扛住重启：网关实例重启、或新加入一个实例后，正在进行中的灰度（哪条规则、当前比例是多少、新旧两个版本各自的内容）不能丢失，重启后仍按重启前的比例继续分流，已经在新桶里的主体依旧在新桶里。这套灰度信息要和规则一样落到持久化存储里，并且沿用现有的多实例热同步通道，任何一个实例上对放量比例的调整，都要即时同步到其余实例，全体按同一个比例分流。

技术栈沿用现有工程：后端 Go 加 Gin 承载 HTTP 与判定网关，计数与放量状态借助 Redis 在多实例间共享，规则与灰度配置持久化到 PostgreSQL，前端仍是 Vue 3 加 TypeScript 的配置与观测台，整套仍用 Docker Compose 一条命令拉起。代码请顺着现有的分层继续拆分，判定入口、算法引擎、多维匹配与多级配额、计数存取、规则持久化各自的边界要保持清晰，新增的灰度分桶与版本选择逻辑应当独立成可单独测试的一层，而不是塞进已有的判定循环里搅在一起。

请附自动化测试锁住这些行为：同一个判定主体在比例不变期间稳定落在同一版本、反复判定结果一致；把比例从小调大时，原本在新版本的主体全部保留、只新增不剔除，主体不被重新洗牌；给定规则、比例与主体，版本归属唯一可复现，且不同「实例」（可用多个独立判定路径模拟）算出的归属完全一致；新旧两个版本的配额计数相互隔离、互不挪用；把放量中止或比例归零后，全部流量立即回到旧版本、新版本计数不再影响判定；比例越界或非法一律被拒绝并说明原因；灰度进行中重启后放量比例与新旧版本内容不丢、继续按原比例分流；一个实例调整比例后其余实例即时按新比例分流。测试要在真实 Redis 与真实（或等价嵌入式）PostgreSQL 上跑通完整链路，而不是打桩糊弄。
